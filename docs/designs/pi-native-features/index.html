方案 4 是共同分叉能力（跨引擎 UX）；方案 1/2/3 是 pi 会话树的呈现形态分歧。

真壳 base 是什么：三稿都直接 @import 仓库真实样式表（src/styles/** + ChatInputBox/styles/**）， 侧栏 / topbar / 消息列 / composer / 右栏 DOM 逐字来自真实客户端运行时 dump（vite dev + 伪 IPC 渲染出的真实 pi 会话页）。 pi 新能力以真实 class 或最小 .pi-* 增量叠加；树数据模型学自旧稿 pi-ui-prototype（会话 = id/parentId 树，时间线 = 激活路径投影）。 仓库样式演进时三稿自动跟随。每稿右上角可开关蓝色角标，页底有「角标 ↔ pi RPC」对照表。
方案 4 · 共同分叉 · mossx 级

同一个 ⑂ 入口 × 三档 capability 落地

分叉做成 mossx 共同原语：pi 走树内新 lane（L3 蓝弹窗）；claude/grok/codex/opencode 走谱系新会话（L2 橙弹窗，侧栏新行带「⑂ 自 #N」徽章可跳回源消息）；gemini/kimi 不渲染入口（L1）。侧栏可切三个引擎会话分别试。

  • 弹窗文案明说本引擎 fork 语义，不说谎
  • 谱系徽章点击跳回源会话源消息（deep link）
  • L2 的正路实现 = Context Compiler 截断投影，不改各家存储
★ 推荐

最终推荐态 · pi 独立增强

= 方案 2 全屏树（深操作主场）＋ 方案 3 tab 分支 chip（日常轻切换）＋ 侧栏 ⑂N 徽标可点开树。补齐方案 2「分支存在感弱」的唯一短板，右栏一个 tab 都不加。只做 pi native 增强，分叉语义 = 树内新 lane。

  • 分叉 → tab 出现「main ▾」，纯文本下拉即切
  • 侧栏「⑂ N」点击 → 直接开全屏树
  • 队列 / ctx 环 / 气泡 ⑂ / 发送方式四稿共享部分原样保留
方案 1

侧栏树 · 面板派

树常驻右栏（新增「树」tab，与文件/Git 平级）。分支存在感最强：lanes、激活路径高亮、旁路暗淡、过滤器、书签全在。

  • 分叉 → 树里立刻长出新 lane
  • steer 送达 → 长成当前 lane 新节点
  • 压缩留痕 = 居中虚线 pill，可回溯
  • 代价：右栏被多占一个 tab；窄窗口下挤
方案 2

沉浸树 · 全屏派

树是「需要时召唤的地图」：topbar「会话树」/ /tree 把消息区换成全屏大画布，Esc 或点节点跳回对话。

  • 对齐 pi TUI /tree 的全屏语义
  • 44px 行高 + lane 标题芯片，适合深树
  • 日常对话视野 100% 留给消息
  • 代价：分支存在感最弱，树用完即走
方案 3

内嵌分叉 · 无面板派

零新增面板、零全屏：分叉只走气泡 hover ⑂；分支只存在于 tab 后缀「main ▾」的纯文本下拉；压缩留可展开的 inline 虚线卡。

  • 分叉后视野不离开对话
  • 实现面最小（无树组件）
  • 代价：没有旁路对比、书签无落点

跨引擎分叉能力调研（本机 CLI 实测 2026-08-21 · 详见 research 文档）

引擎fork树对本设计的含义
pi 0.84✅ --fork + RPC fork/clone✅ 真树（id/parentId + /tree + 分支摘要）三稿的主角
claude✅ --fork-session（复制续跑）可推导（parentUuid/sidechain）+ 已有 rewind可共享「气泡 ⑂ 分叉」入口；树走 rewind，不进本期
codex✅ codex fork 子命令❌同上
grok✅ --fork-session❌同上
opencode✅ --fork（with --continue/--session）❌同上
gemini / kimi❌ 仅 resume/continue❌分叉入口对其置灰（capability 驱动）
dsh✅ matrix 已标 supportedunknown自家 harness，可对齐语义

结论：分叉是可推广的原语（同入口、按 capability 换文案），树是 pi 专属。所以无论选哪个方案，「气泡 ⑂ 分叉」都应设计成多引擎共享；树面板 / 全屏树只挂 pi。
